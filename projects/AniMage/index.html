what it is

AniMage is an anime platform: streaming, manga, and watch parties. i don't host any content. the site is a middleman that asks a bunch of apis for stuff and shows you the answers.

6upstream apis
30max per watch room
4hinvite ttl
2sqlite dbs

the story

  • it started with one annoying problem. i got tired of opening five sites to watch one show. different players, different ads, different broken episodes. so i wrote a python proxy that forwarded requests to one api and rendered the results. v1 was about a hundred lines.
  • then streams kept dying. the apis i was proxying were flaky, so i vendored two reverse-engineered backends into the repo and ran them as subprocesses on their own ports. i started caching in sqlite too, because popular shows were hammering the upstreams on every request.
  • then my friends wanted in. i didn't want to hand the site to the whole internet, so i added invite codes with pins. they expire after four hours if nobody uses them, and the server rate limits failed attempts.
  • then watching together got annoying. screen sharing on discord works until someone's stream lags, so i built a separate sync server. up to thirty people per room, the host controls playback, everyone else follows along. there's guest chat, and idle rooms get purged after thirty minutes.
  • then i had to ship it. docker, nginx, a discord bot to hand out invites, a mac app, chromecast support, a filler api so you can skip the canon filler. it's a lot now. also it blocks curl, because bots kept scraping the api. if your user agent doesn't look like a browser, you get a 403.

the pipes

everything sits behind one python proxy. it does the auth, the rate limiting, the caching, and flattens every upstream into the same response shape, so the frontend doesn't care where a show came from.

anilistsearch and metadata · graphql

the frontend sends a graphql query, the proxy forwards it to graphql.anilist.co with a browser user agent. no auth needed, they're polite about rate limits.

miruro apistream sources · vendored backend

a reverse-engineered backend for a site that encrypts its requests through a "secure pipe" tunnel. this backend skips the encryption and exposes plain rest endpoints. it uses curl_cffi with chrome tls fingerprints to get past cloudflare. i vendored it into the repo and run it as a uvicorn subprocess, then proxy to it and cache the popular results.

anivexa apistream aggregator · vendored backend

an aggregator. it wraps a bunch of streaming sources behind one endpoint, so a show has a backup provider if a source dies mid-season. same setup as miruro: vendored, subprocess, proxied, cached.

anikotoraw relay

the one i started with. requests to /anikoto/* get relayed straight upstream with a spoofed user agent. no caching, no normalization, just a pipe.

mangadexmanga · official api

the manga reader uses the official mangadex api. it's documented and it behaves, which was a nice break.

filler apiepisode metadata · vendored node service

a small node service that knows which episodes of a show are filler. the frontend uses it to mark them so you can skip the canon filler.

what a search actually looks like

you type something in the search bar, this is what happens. the frontend fires a graphql query, the proxy checks your invite, forwards it, and hands back the result:

# frontend → proxy (authed)
POST /api/anilist X-Invite-Code: dsplay
{ query: "{ Page(...) { media { title { romaji } } } }" }

# proxy → anilist.co
POST https://graphql.anilist.co User-Agent: AniMage/1.0

# proxy ← anilist
200 {"data":{"Page":{"media":[{"title":{"romaji":"Cowboy Bebop"}}, ...]}}}

# frontend ← proxy
200 same shape, cached for next time

the watch party server is separate, with its own database. rooms, members, sync state, guest chat. when the host presses play, a broadcast tells every other player in the room to match.
